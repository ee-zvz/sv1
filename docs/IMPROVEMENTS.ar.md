# SV1 1.5.0 — مراجعة السوق وخطة التطوير

التاريخ: 2026-10-28

هذه الصفحة تلخّص البحث الذي سبق إصدار `1.5.0`. قارنّا سطح الميزات المعلن في
الأدوات التي نقارن أنفسنا بها، ثم فصلنا بين ما يحسّن **جودة الدليل** وما يضيف
**عرضاً فقط**. النتيجة: SV1 لا تنافس Burp أو ZAP أو Nuclei في عدد الفحوصات،
لكنها تستطيع أن تكون الخيار الأول في فئة أضيق: **إثبات XSS وSQLi وSSRF** مع
دليل تنفيذ حقيقي.

## الخلاصة

الفوز في «كل شيء» غير واقعي. Burp وZAP يملكان مصادقة، إضافات، تكاملات، وفحوصات
لا حصر لها. SV1 يملك ما هو أهم في فئته:

1. `HIGH` لا يُمنح لانعكاس نص، بل لعلامة نُفّذت داخل Chromium.
2. الصفحات المتغيرة تُقاس قبل قبول أي قرار boolean أو time.
3. كل نتيجة مقبولة تُعاد قبل تثبيتها، وما لا يتكرر يُخفّض.
4. النطاق، إعادة التوجيه، والجلسة حدود صارمة لا «أفضل جهد».

`1.5.0` أغلق ثلاث فجوات كانت تمنع استخدام هذا النموذج على تطبيق حقيقي:
تسجيل الدخول، اكتشاف الصفحات، وإمكانية استكمال الفحص. وأضاف تصنيفاً قياسياً
للنتيجة كي تصلح للتقارير وSARIF دون خريطة يدوية.

## ما تقدمه الأدوات المنافسة

| الأداة | ما يهمنا من ميزاتها المعلنة |
|---|---|
| Burp Suite Professional / DAST | زحف وتدقيق، فحص بالمتصفح، بيانات دخول بسيطة وتسلسل دخول مسجّل، API وGraphQL وWebSocket، BChecks، إضافات، SARIF وCI |
| OWASP ZAP | فحص active/passive، مصادقة واستراتيجيات تحقق، معالجة Anti-CSRF، OAST، GraphQL وOpenAPI وWebSocket، سكربتات، API وأتمتة |
| dalfox v3 | XSS reflected/stored/DOM، تحليل واستخراج المعاملات، بصمة WAF ومحاولات التجاوز، بايلودات مخصصة، JSON/JSONL/SARIF، خادم REST وMCP |
| sqlmap | عمق استغلال SQLi حسب DBMS، tamper scripts، قنوات OOB، بصمة، سحب بيانات، وصول للملفات والنظام |
| Nuclei | قوالب للويب والشبكة، مكتبة قوالب كبيرة، مخرجات CI وتكاملات |

الفجوات كانت واضحة: المصادقة قبل الزحف، ملف تقدّم دائم، `robots.txt` و
`sitemap.xml`، تصنيف CWE/OWASP وإصلاح مقترح، ثم GraphQL/WebSocket وOpenAPI
بصيغة YAML وتسلسل دخول مسجّل.

## ما أُضيف في 1.5.0

### 1. تسجيل الدخول قبل الزحف

`--login URL` يجلب صفحة الدخول، يجد نموذج POST على نفس الأصل فيه حقل password،
يحافظ على hidden CSRF، ويرسل بيانات الدخول مرة واحدة. الكوكيز تبقى في جلسة
HTTP الحية وتُستورد إلى Chromium قبل الإثبات.

```powershell
$env:SV1_USERNAME = "operator"
$env:SV1_PASSWORD = "correct horse battery staple"
python sv1.py -u https://app.tld/dashboard --login https://app.tld/login `
  --login-check "Sign out" --crawl --xss --sqli
```

- `--login-check TEXT` هو اختبار النجاح الموثوق. بدونه يُقبل تغيّر الكوكي أو
  إعادة التوجيه، لكن يظهر تحذير أن الجلسة غير مؤكدة.
- حقل اسم المستخدم لا يُهاجم افتراضياً، ولا في مراحل stored/blind/second-order.
  `--login-attack` هو الخيار الصريح؛ فحص بيانات الدخول قد يقفل الحساب.
- كلمة المرور لا تُطبع ولا تُكتب في checkpoint أو history. يُفضّل
  `SV1_PASSWORD` على `--password` الظاهر في سطر الأوامر.
- OAuth وSSO وتسجيل الدخول المعتمد على JavaScript أو MFA يحتاج
  `--storage-state` أو HAR أو تسلسل متصفح مسجّل. هذه حدود معلنة.

### 2. استكمال الفحص من checkpoint

`--resume FILE` يكتب JSON ذرّياً بعد كل نقطة منتهية. الملف يحمل النقاط، المفاتيح
المكتملة، النتائج، وخيارات الفحص. التشغيل الثاني يتجاوز النقاط المكتملة ويعيد
النتائج التي نجت من التحقق.

```powershell
python sv1.py -u https://app.tld --crawl --xss --sqli --resume scan.json
# انقطع الفحص؟
python sv1.py -u https://app.tld --crawl --xss --sqli --resume scan.json
```

يتحقق الملف من الهدف ومن خيارات الفحص واكتشاف النقاط الجوهرية، ويرفض الخلط
بين هدفين، أو مجموعتي فحص مختلفتين، أو تشغيل مسجّل وتشغيل مجهول. مراحل Chromium
وDOM وstored وblind وreplay تُعاد لأنها تعتمد على الصفحة الحية والـcallbacks؛
الذي يُستكمل هو مرحلة النقاط الطويلة. هذا استكمال على مستوى النقاط، وليس ادعاء
محرك async كامل.

كوكيز الجلسة لا تُحفظ في الـcheckpoint. أكمل الفحص المسجّل بنفس خيارات
`--login` ليُعاد بناء الجلسة قبل إرسال الحمولات المعلّقة. الملف قد يحتوي قوالب
طلبات وأوامر curl فيها هيدرات أو كوكيز جلسة مستوردة من HAR. تعامل معه كملف
حساس محلي. لا يحتوي كلمة مرور تسجيل الدخول.

### 3. اكتشاف الصفحات من robots وsitemap

`--sitemap` يقرأ `robots.txt`، يتبع حتى ثلاثة ملفات sitemap على نفس الأصل،
ويضيف روابط الصفحات إلى قائمة الزحف. فهارس sitemap تُتبع مستوى واحداً. المواقع
الخارجية والملفات الثنائية والروابط خارج النطاق لا تُضاف.

```powershell
python sv1.py -u https://site.tld --crawl --sitemap --xss --sqli
```

حدود العمق وعدد الصفحات وقواعد النطاق تبقى كما هي؛ sitemap يغيّر بذور الزحف فقط.

### 4. تصنيف النتيجة وخطة الإصلاح

كل نتيجة XSS أو SQLI أو SSRF تحمل الآن:

- `cwe` — CWE-79 أو CWE-89 أو CWE-918؛
- `owasp` — A03:2021 Injection أو A10:2021 SSRF؛
- `remediation` — اتجاه إصلاح قصير مناسب للفئة.

يظهر التصنيف في الكونسول، HTML، CSV (بما فيها `remediation`)، JSON، وخصائص
SARIF. هذه بيانات وصفية، وليست ثغرة جديدة ولا تغييراً في الشدة.

## ما تبقّى في الخطة

| الأولوية | البند | لماذا |
|---|---|---|
| P1 | دخول مسجّل بالمتصفح / OAuth وSSO | النموذج البسيط لا يكفي تطبيقات المؤسسات |
| P1 | محرك HTTP غير متزامن | thread pool يعمل، لكن الفحوصات الطويلة تحتاج جدولة وإلغاء أفضل |
| P1 | GraphQL وWebSocket | مدخلات API الحديثة ليست كلها نماذج HTML |
| P1 | OpenAPI YAML واكتشاف تلقائي | مواصفات أكثر وإعداد أقل |
| P2 | بايلودات وقوالب مخصصة | إضافة فحص دون تعديل Python |
| P2 | SQLi عبر OOB وNoSQL | توسيع نموذج الإثبات لقواعد بيانات أخرى |
| P2 | تتبع DOM ديناميكي | source→sink الثابت يفوّت القيم المجمّعة وقت التشغيل |
| P2 | API/MCP/إضافات | تكامل الفريق، لا جودة الكشف |
| P3 | فحوصات غير حقن واسعة | هنا يفوز Burp/ZAP/Nuclei؛ ليست فئة SV1 |

## ما لا نريد تقليده

- عدد البايلودات ليس نتيجة. الدليل وإعادة الإثبات هما المعيار.
- لا نتيجة لمجرد انعكاس؛ الانعكاس يبقى `MEDIUM`.
- لا نتحول إلى إطار استغلال واستيلاء على قواعد البيانات؛ sqlmap يملك هذا
  المسار.
- لا نضيف مئات الفحوصات منخفضة الثقة ونضعف الإشارة التي تميّز SV1.
